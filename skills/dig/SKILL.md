プラン・設計・意思決定のあらゆる側面について、共通の理解に達するまでユーザーに徹底的に質問する。甘い回答や曖昧な返答には突っ込む。

## 開始

参照できる会話全体（dig 開始前を含む）と、同じテーマの既存の dig log（議論を記録する Markdown）を、末尾の形式で整理する。参照できない履歴は推測せず明示する。

最初のラウンドの前に、掘る量を1問だけ聞く（`AskUserQuestion` が使えればダイアログで）。
- **軽め**：重要な枝だけ、5問前後で終える。
- **ふつう**（推奨）：主要な枝をひととおり掘る。
- **徹底的に**：すべての枝を、新たな洞察が出なくなるまで掘る。
会話や依頼文から掘る量が明らかなときは聞かずに決め、その旨を一言伝える。選んだ掘る量は dig log の「目的・前提・制約」に記録し、途中で変更を求められたら従う。

保存先はユーザー指定、なければ `docs/dig/YYYY-MM-DD-<slug>.md`。1テーマ1ファイルとし、再開時は既存の dig log を更新する。新規作成での上書きは避け、候補が曖昧なら確認する。

## 設計ツリーとラウンド

対象を設計ツリーとして捉える。各判断から、その判断に依存する次の判断が枝分かれする。

**フロンティア**＝前提がすべて解決済みの未決定事項。各ラウンドでは、フロンティアから互いに依存しない質問を**最大3問**選んで一度に聞く。同じラウンド内の別の質問の答え次第で変わる質問は、次のラウンドに回す。

選ぶときは「深さ」を優先する。いま掘っている枝の質問を先に選び、その枝で新たな洞察が出なくなってから別の枝へ移る。重大で、後から変えにくい判断（データ形式、構成、公開範囲など）は単独で1問のラウンドにしてよい。

## 質問の出し方

各ラウンドは2段で行う。

1. **チャットに文脈を書く**。質問ごとに次の形式で、なぜ重要かと推奨理由を示す。

   ```
   ### ❓ Q[番号]: [質問文]
   [なぜこの質問が重要か]
   **推奨: [選択肢名]** — [理由]
   ```

2. **`AskUserQuestion` ツールでダイアログを出す**。チャットに書いた質問を、そのまま1回の呼び出しにまとめる。
   - `header` は12文字以内で `Q[番号] 短い題` とする。
   - 選択肢は2〜4個。推奨案を先頭に置き、`label` の末尾に「（推奨）」を付ける。`description` に一行で結果やトレードオフを書く。
   - 「その他」は自動で付くので、選択肢に入れない。
   - 複数を選べる問いだけ `multiSelect: true` にする。

次のときはダイアログを使わず、1. の形式に `- **A** — …` の選択肢リストを足してチャットで聞く。
- `AskUserQuestion` が使えない（サブエージェント内、ツール無効など）。
- 選択肢が5個以上、または自由記述でしか答えられない問い。

## 事実は自分で調べる

環境を調べれば分かる事実は自分で確認し、ユーザーには聞かない。必要に応じてツールやサブエージェントで調査する。調査中の事実に依存する質問は後回しにし、それ以外のフロンティアを先に聞く。ユーザーに聞くのは、選択やトレードオフを伴う意思決定だけ。

## 記録

開始時と**各ラウンドの回答後**に dig log を更新し、保存を確認してから次のラウンドへ進む。ユーザーには取り込んだ内容や更新差分を短く示す。回答で前の決定が覆ったら「撤回・置換済み」に移す。

## 壊れ方の確認

フロンティアが空になったら、終了確認の前に一度だけ、決定事項全体に対して「どうなると失敗するか」を最大3つ挙げる（例：想定外の入力、規模の増加、後からの仕様変更、依存先の変更）。各項目について「手当てする（決定を追加・変更）」「受け入れる（リスクとして記録）」を1ラウンドで聞く。手当てで新しい未決定事項が出たら、フロンティアに戻してラウンドを続ける。受け入れたものは dig log の「既知のリスク」に記す。掘る量が「軽め」のときは最大1つでよい。

## 終了

壊れ方の確認を終え、フロンティアが空で、重要な枝に暗黙の前提が残っていなければ、共通理解に達したかをユーザーに確認する（`AskUserQuestion` で「達した／まだ続ける」を聞いてよい）。ユーザーが確認するまで、実装や計画作成には移らない。続行を求められたら設計ツリーを更新し、ラウンドを続ける。

終了時は dig log と参照できる会話を照合し、抜けや状態の誤りを修正する。dig log は残し、ユーザーには全文ではなく下記の要約を返す。

以下の両形式では、該当しない節は省略する。

終了時の報告の形式:
```markdown
## まとめ

dig log: [テーマ](保存先のパス)

### 主な決定
- [主要な決定を短く記す]

### 未決・保留
- [残る論点と、確定に必要な確認]

### 次の作業
- [ ] [決定から導いた具体的なタスク。依存順に並べる]
```

## 次の作業への出口

共通理解の確認が取れたら、決定事項から**次の作業一覧**を作って dig log の「次の作業」に書き、終了報告にも載せる。
- 1項目は「何を・どこで・完了条件」が分かる粒度にし、依存する順に並べる。コードがあるなら対象のファイル・シーン・スクリプトを書く。
- 決定にない作業を勝手に足さない。必要そうなら「未決・保留」に回す。
- 最後に、次をどうするかを1問で聞く：「この一覧で実装を始める」「仕様書・計画にまとめる」「ここで終える」。ユーザーが選ぶまで実装には移らない。

dig log の形式（開始時からこの構成で更新）:
```markdown
# dig log: [テーマ]

## 目的・前提・制約
- [達成したいこと、確認した前提、守る制約]

## 決定事項
- [合意した決定ごとに記載。数値・条件・例外・禁止事項も省略しない]
  - 理由: [判断理由。分かる場合のみ]
  - 出典: [開始前の発言の要旨、Q番号など]

## 対象外
- [今回やらないこと]

## 未決・保留
- [未解決の論点。未合意の提案はその旨と、確定に必要な確認を記す]

## 既知のリスク
- [壊れ方の確認で受け入れたリスクと、受け入れた理由]

## 次の作業
- [ ] [決定から導いたタスク。依存順]

## 撤回・置換済み
- [以前の決定と変更理由、置き換えた決定]
```
